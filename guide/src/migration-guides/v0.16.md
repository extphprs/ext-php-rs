# Migrating to `v0.16`

## `Zval::set_resource` Requires an Unsafe Block

`Zval::set_resource` accepts a raw `zend_resource` pointer and transfers one
owned Zend reference into the zval, so callers must now uphold its safety
contract explicitly.

### Before (v0.15)

```rust,ignore
zval.set_resource(resource);
```

### After (v0.16)

```rust,ignore
// SAFETY: `resource` is a valid Zend-managed resource whose owned reference is
// transferred into `zval`.
unsafe { zval.set_resource(resource) };
```

The pointer must be non-null and valid until Zend releases the transferred
reference. `set_resource` does not increment the resource refcount, so the
caller must relinquish that reference after the call. Replacing a zval with the
same resource requires a separate incoming reference.

## SAPI Header Raw Constructors Removed

`SapiHeader::from_raw` and `SapiHeaders::from_raw` have been removed. These
constructors accepted unchecked Zend pointers through safe Rust.

ext-php-rs now copies the header data into owned snapshots before invoking the
`Sapi::send_header` and `Sapi::send_headers` callbacks.

### Before (v0.15)

```rust,ignore
let header = SapiHeader::from_raw(raw_header);
let headers = SapiHeaders::from_raw(raw_headers);
```

### After (v0.16)

Read header data from the snapshots supplied to your `Sapi` implementation:

```rust,ignore
fn send_header(_ctx: &mut MyContext, header: &SapiHeader) {
    if let Some((name, value)) = header.as_name_value() {
        // Send the header to the client.
    }
}

fn send_headers(
    _ctx: &mut MyContext,
    headers: &SapiHeaders,
) -> SendHeadersResult {
    let response_code = headers.http_response_code();
    SendHeadersResult::DoSend
}
```

Code that needs direct access to `sapi_header_struct` must use the raw FFI API
and uphold Zend's pointer validity and lifetime requirements itself.

## Void Return Type for Functions Without Explicit Return

Functions and methods without an explicit Rust return type now declare `void` as their PHP return type.

### Before (v0.15)

```rust,ignore
#[php_function]
pub fn do_something() {
    println!("Hello");
}
```

Generated PHP signature: `function do_something()` (implicit `mixed` return)

### After (v0.16)

The same Rust code now generates: `function do_something(): void`

### Migration

If your function actually returns a value but didn't declare it, you must now add the return type:

```rust,ignore
// Before: worked but was incorrect
#[php_function]
pub fn get_value() {
    42  // implicitly returned, but no declared type
}

// After: must declare return type
#[php_function]
pub fn get_value() -> i32 {
    42
}
```

### Exceptions

The magic methods `__destruct` and `__clone` are excluded from this change, as PHP forbids return type declarations on them.

## Mutable Accessors Require `&mut`

This closes [#461](https://github.com/extphprs/ext-php-rs/issues/461).

Several safe functions used to hand out a `&mut` derived from a shared `&`. That
let ordinary safe code hold two mutable references to the same zval at once,
which is undefined behaviour under Rust's aliasing rules. The signatures below
now require a mutable borrow so the compiler rejects that.

The affected functions are `ZendHashTable::get_mut`,
`ZendHashTable::get_index_mut`, `Zval::indirect_mut`,
`ExecutorGlobals::function_table_mut`, `Zval::traversable`, `Zval::iterable`,
`ClassEntry::get_iterator`, and `StreamWrapper::get` / `StreamWrapper::get_mut`.

### Mutable Hashtable Access

`get_mut` and `get_index_mut` take `&mut self`, so the binding must be mutable.

#### Before (v0.15)

```rust,ignore
fn bump(ht: &ZendHashTable) {
    if let Some(zv) = ht.get_mut("counter") {
        zv.set_long(1);
    }
}
```

#### After (v0.16)

```rust,ignore
fn bump(ht: &mut ZendHashTable) {
    if let Some(zv) = ht.get_mut("counter") {
        zv.set_long(1);
    }
}
```

The following no longer compiles, which is the point of the change:

```rust,ignore
let first = ht.get_mut("test").unwrap();
let second = ht.get_mut("test").unwrap();  // error[E0499]
first.set_long(2);
```

If you need to read two entries at once, take the second as a shared reference
with `get`, or finish with the first before requesting the second.

### Executor Globals

`function_table_mut` takes `&mut self`, so acquire the write guard rather than
the read guard.

#### Before (v0.15)

```rust,ignore
let table = ExecutorGlobals::get().function_table_mut();
```

#### After (v0.16)

```rust,ignore
let mut globals = ExecutorGlobals::get_mut();
let table = globals.function_table_mut();
```

`GlobalWriteGuard` already implements `DerefMut`, so no other change is needed.
Bind the guard to a variable, as the guard must outlive the borrow.

### Iterables and Traversables

`Zval::traversable` and `Zval::iterable` take `&mut self`, and `Iterable` is now
extracted through `FromZvalMut` instead of `FromZval`. Resolving the
`Traversable` variant invokes the Zend `get_iterator` handler, which mutates the
object, so a shared borrow was never sound.

Function signatures using `Iterable` as a parameter are **unchanged** and keep
working, because the macro already extracts arguments through `FromZvalMut`:

```rust,ignore
#[php_function]
pub fn count_items(mut iterable: Iterable) -> usize {
    iterable.iter().map_or(0, Iterator::count)
}
```

Only hand-written extraction needs updating.

#### Before (v0.15)

```rust,ignore
let iterable = Iterable::from_zval(zval);
let iterator = zval.traversable();
```

#### After (v0.16)

```rust,ignore
let iterable = Iterable::from_zval_mut(zval);
let iterator = zval.traversable();
```

where `zval` is now a `&mut Zval`. `ClassEntry::get_iterator` likewise takes
`&'a mut Zval` and ties the returned iterator's lifetime to it.

### Stream Wrappers

`StreamWrapper::get` and `StreamWrapper::get_mut` are now `unsafe`. They return a
reference into PHP's per-request stream wrapper table with a lifetime that is not
constrained by their arguments, and `get_mut` cannot verify that no other
reference to the same wrapper is live. This is the same class of change as
`Zval::set_resource` above.

#### Before (v0.15)

```rust,ignore
let wrapper = StreamWrapper::get_mut("http").unwrap();
```

#### After (v0.16)

```rust,ignore
// SAFETY: used within the current request, and no other reference to the
// `http` wrapper is live for the duration of this borrow.
let wrapper = unsafe { StreamWrapper::get_mut("http") }.unwrap();
```

Both functions also copy the name into a NUL-terminated C string before calling
into PHP. Previously they passed the bytes of a `&str` directly, and
`php_stream_locate_url_wrapper` scans the path until it reaches a character
outside `[A-Za-z0-9+-.]`, so it could read past the end of the string slice and
resolve the wrong wrapper.

### Threading `&mut` Through a Handler

The requirement can propagate up several frames. A realistic case: a function
that mutates entries of an array argument.

#### Before (v0.15)

```rust,ignore
#[php_function]
pub fn normalise(ht: &ZendHashTable) {
    rescale(ht);
}

fn rescale(ht: &ZendHashTable) {
    for key in ["width", "height"] {
        if let Some(zv) = ht.get_mut(key) {
            if let Some(value) = zv.long() {
                zv.set_long(value * 2);
            }
        }
    }
}
```

#### After (v0.16)

```rust,ignore
#[php_function]
pub fn normalise(ht: &mut ZendHashTable) {
    rescale(ht);
}

fn rescale(ht: &mut ZendHashTable) {
    for key in ["width", "height"] {
        if let Some(zv) = ht.get_mut(key) {
            if let Some(value) = zv.long() {
                zv.set_long(value * 2);
            }
        }
    }
}
```

`&mut ZendHashTable` is accepted as a `#[php_function]` parameter type, so the
PHP-facing signature does not change. If you cannot obtain a mutable borrow at
the outermost frame, the array is genuinely shared and mutating it was unsound
before this release.

## Engine-Input Accessors Return `Option` Instead of Panicking

Accessors that read data controlled by the engine or the request used to
`panic!`, which aborts the process inside an `extern "C"` frame. They now
return `Option` and align with `http_server_vars`, which already did.

Affected signatures:

| Before (v0.15) | After (v0.16) |
|---|---|
| `ProcessGlobals::http_get_vars() -> &ZendHashTable` | `-> Option<&ZendHashTable>` |
| `ProcessGlobals::http_post_vars() -> &ZendHashTable` | `-> Option<&ZendHashTable>` |
| `ProcessGlobals::http_cookie_vars() -> &ZendHashTable` | `-> Option<&ZendHashTable>` |
| `ProcessGlobals::http_env_vars() -> &ZendHashTable` | `-> Option<&ZendHashTable>` |
| `ProcessGlobals::http_files_vars() -> &ZendHashTable` | `-> Option<&ZendHashTable>` |
| `ProcessGlobals::http_request_vars() -> Option<&ZendHashTable>` | `-> Result<Option<&ZendHashTable>>` |
| `SapiHeader::as_str() -> &str` | `-> Option<&str>` |
| `SapiHeader::name() -> &str` | `-> Option<&str>` |
| `zend::php_sapi_name() -> String` | `-> Option<String>` |

`http_request_vars` distinguishes engine failures from absence: `Err` carries
`Error::AutoGlobalLoadFailed("_REQUEST")` or `Error::ZvalConversion` where it
previously panicked, and `Ok(None)` means the global is not populated.
`SapiHeader::value` keeps its `Option` signature but returns `None` where it
previously panicked (non-UTF-8 header).

### Before (v0.15)

```rust,ignore
let get = ProcessGlobals::get().http_get_vars().to_owned();
let name = header.name();
```

### After (v0.16)

```rust,ignore
let get = ProcessGlobals::get().http_get_vars()?.to_owned();
let name = header.name()?;
```

`None` means the global has not been populated as an array (yet) or, for
headers, that the bytes are not valid UTF-8. In a regular request context the
superglobals are populated and unwrapping stays reasonable; before request
startup or in exotic SAPIs it no longer aborts the process.

## `describe` Types Moved to `ext-php-rs-introspection`

The types behind `ext_php_rs::describe` now live in the
`ext-php-rs-introspection` crate, which has no dependency on the Zend engine.
`cargo-php` depends on that crate alone, so installing it no longer needs PHP.
The paths under `ext_php_rs::describe` are unchanged re-exports. Three details
of the ABI changed with the move.

### `DataType` Zend Conversions Moved to `DataTypeExt`

`DataType` is defined in the new crate, so the conversions that need the Zend
`IS_*` constants moved to the `DataTypeExt` trait, exported from the prelude.

#### Before (v0.15)

```rust,ignore
let raw = DataType::Long.as_u32();
let ty = DataType::from(raw);
```

#### After (v0.16)

```rust,ignore
use ext_php_rs::prelude::*;

let raw = DataType::Long.as_u32();
let ty = DataType::from_u32(raw);
```

### `describe::Class::flags` Replaced by `is_interface`

`Class` carried the raw `ce_flags` word. It now carries the only bit stub
generation needs.

#### Before (v0.15)

```rust,ignore
let is_interface = ClassFlags::from_bits(class.flags)
    .unwrap_or(ClassFlags::empty())
    .contains(ClassFlags::Interface);
```

#### After (v0.16)

```rust,ignore
let is_interface = class.is_interface;
```

### Tuple `From` Impls for `Method` and `Constant` Removed

`describe::Method` and `describe::Constant` are now defined outside
`ext-php-rs`, and Rust forbids implementing `From<(A, B)>` for a foreign type,
so these conversions are gone: `From<(FunctionBuilder, MethodFlags)> for
Method`, `From<(String, Box<dyn IntoConst + Send>, DocComments)> for Constant`
and `From<(String, DocComments)> for Constant`. `ext-php-rs` uses private
helpers internally. Downstream code that built these values by hand can fill
the structs directly, every field is public.

#### Before (v0.15)

```rust,ignore
let constant: Constant = ("MY_CONST".to_string(), docs).into();
```

#### After (v0.16)

```rust,ignore
let constant = Constant {
    name: "MY_CONST".into(),
    docs: docs.into(),
    value: abi::Option::None,
};
```

### `Description::version` Is the Introspection Version

`Description::version` was a `&'static str` holding the `ext-php-rs` version.
It is now the first field, an `abi::Str` holding the `ext-php-rs-introspection`
version. The entry point is renamed `ext_php_rs_describe_module_v2` and returns
`*mut Description` allocated with `Box::into_raw` instead of a `Description` by
value; the new name keeps a v0.15 extension and a v0.16 `cargo-php` (or the
reverse) from calling each other with the wrong calling convention. Only the
`#[php_module]` macro emits that symbol, so this matters solely if you
implement it by hand. `cargo php stubs` reads the version through the pointer
before touching anything else, and
`cargo php stubs` accepts an extension whose version is semver compatible with
the one the CLI was built with. `Module::enums` is always present and
`Class::closure()` is always available; the `enum` and `closure` features only
decide whether `ext-php-rs` fills them.


## `PackSlice::unpack_into` Requires an Unsafe Block

`PackSlice::unpack_into` builds a `&[T]` over the bytes of a `zend_string`, so
its length and alignment preconditions are now part of the signature.
`Zval::binary_slice` checks both and stays safe. `Pack::unpack_into` stays safe
as well: it now reads unaligned and never relied on alignment.

### Before (v0.15)

```rust,ignore
let values: &[u64] = u64::unpack_into(zend_str);
```

### After (v0.16)

```rust,ignore
// Preferred: the checked entry point.
let values: &[u64] = zval.binary_slice::<u64>()?;

// Or, when the checks are done by hand:
// SAFETY: `zend_str.len` is a multiple of 8 and `val` is 8-byte aligned.
let values: &[u64] = unsafe { u64::unpack_into(zend_str) };
```

`Zval::binary_slice` also returns `None` when the string bytes are not aligned
for `T`. Zend allocates every string on an 8-byte boundary, so this only fires
for types wider than 8 bytes or strings from a foreign allocator.

## `Zval::set_ptr` Requires an Unsafe Block

`Zval::set_ptr` stores a raw pointer in an `IS_PTR` zval. The engine reads
`IS_PTR` entries with a fixed type in several of its tables (property tables as
`zend_property_info *`, constant tables as `zend_class_constant *`, INI
directives as `zend_ini_entry *`), so storing an arbitrary pointer and letting
the zval reach one of those tables is undefined behaviour.

### Before (v0.15)

```rust,ignore
zval.set_ptr(ptr);
```

### After (v0.16)

```rust,ignore
// SAFETY: `ptr` outlives the zval and the zval never reaches an engine table.
unsafe { zval.set_ptr(ptr) };
```

`set_ptr` now also releases the previous value of the zval instead of
overwriting it in place.

## Iterators Yield Owned Values

`ZendIterator::get_current_data` returned `&'a Zval` with an unconstrained
`'a`, so callers could keep the reference past the next `move_forward`. Zend
releases that zval on every step (`zend_user_it_invalidate_current` runs
`zval_ptr_dtor` on it), so the reference dangled. The reference is now tied to
the `&mut self` borrow, and both `ZendIterator`'s and `Iterable`'s `Iter` yield
`(Zval, Zval)`: the value is a shallow clone, the same copy `foreach` makes in
`ZEND_FE_FETCH_R`.

### Before (v0.15)

```rust,ignore
let values: Vec<&Zval> = iterator.iter()?.map(|(_, v)| v).collect();
```

### After (v0.16)

```rust,ignore
let values: Vec<Zval> = iterator.iter()?.map(|(_, v)| v).collect();
```

Destructuring `for (k, v) in iterator.iter()?` keeps working; `v` is a `Zval`
instead of a `&Zval`, so drop the explicit `&` where you spelled the type.

## `ZBox::into_raw` Returns `*mut T`

`ZBox::into_raw` fabricated a `&'static mut T`. It now mirrors `Box::into_raw`
and returns `*mut T`, which `ZBox::from_raw` accepts back unchanged.

### Before (v0.15)

```rust,ignore
let obj: &'static mut ZendObject = zbox.into_raw();
zval.set_object(obj);
```

### After (v0.16)

```rust,ignore
let obj: *mut ZendObject = zbox.into_raw();
// SAFETY: `into_raw` yields a valid, exclusively owned object.
zval.set_object(unsafe { &mut *obj });
```

## Heap-Leaking `into_raw` Constructors Removed

`FunctionEntry::into_raw`, `IniEntryDef::into_raw`, `SapiModule::into_raw` and
the deprecated `ModuleEntry::into_raw` boxed a value and returned the pointer
with no owner. None of them was needed: `ModuleBuilder` and `ClassBuilder` hand
function tables to the engine themselves, `IniEntryDef::register` takes a
`Vec`, and `sapi_startup`/`php_module_startup` copy the `sapi_module_struct`
by value (`sapi_module = *sf`), so a local is enough.

### Before (v0.15)

```rust,ignore
let sapi = builder.build()?.into_raw();
unsafe { sapi_startup(sapi) };
// ...
unsafe { cleanup_sapi_allocations(sapi); drop(Box::from_raw(sapi)) };
```

### After (v0.16)

```rust,ignore
let mut sapi = builder.build()?;
unsafe { sapi_startup(&raw mut sapi) };
// ...
unsafe { cleanup_sapi_allocations(&raw mut sapi) };
```

Keep the `SapiModule` alive until `sapi_shutdown()` has returned: the engine
copies the struct but keeps reading the strings it points to.

## `GlobalConstantFlags::CaseSensitive` Removed

The flag was deprecated and had no effect since PHP 8.0, where constants are
always case-sensitive. Remove it from any flag set you build.

## `alloc::emalloc` Honours `Layout::align`

`emalloc` ignored the alignment of the `Layout` it was given. The Zend allocator
guarantees `ZEND_MM_ALIGNMENT` (8 bytes) and has no aligned-allocation entry
point, so `emalloc` now returns a null pointer for any `Layout` whose alignment
exceeds 8 instead of handing back under-aligned memory.

## `zend::cleanup_module_allocations` Removed

The helper freed the module's function table, argument info and strings during
MSHUTDOWN. That is unsound on every supported PHP version:

- For a `dl()`-loaded extension, `module_destructor` calls
  `zend_unregister_functions(module->functions, …)` **after** the shutdown
  function returns, and that walks the table reading `fname`.
- `zend_register_functions` copies the `arg_info` array only shallowly, so
  `arg_info[i].name` and `.default_value` stay borrowed by the engine and are
  read at runtime by `ReflectionParameter`. A function with neither parameters
  nor a return type keeps the array itself.

There is no replacement, and nothing to call. ext-php-rs now reclaims class and
enum method tables as soon as the engine has interned them, and owns the tables
the engine borrows for the life of the process. Extensions must not free
anything they pass to `zend_register_*`.

### Before (v0.15)

```rust,ignore
unsafe { ext_php_rs::zend::cleanup_module_allocations(entry) };
```

### After (v0.16)

Delete the call. If you set `module_shutdown_func` through
`ModuleBuilder::shutdown_function`, it is no longer wrapped and runs exactly as
you wrote it.

## Registration Tables Are Owned Per Extension

ext-php-rs no longer keeps a crate-wide list of the tables the Zend engine
borrows for the life of the process. Each table is owned by a `static` belonging
to the extension, the way a C extension owns its `zend_module_entry`,
`zend_function_entry[]` and `zend_internal_arg_info[]`.

Three signatures changed.

### `FunctionBuilder::build`

Returns the argument info table alongside the entry, so the caller decides where
it lives. Dropping it dangles every registered function.

```rust,ignore
// v0.15
let entry = builder.build()?;

// v0.16
let (entry, arg_info) = builder.build()?;
```

`ClassBuilder` and `EnumBuilder` do this for you: `registration` now receives the
tables alongside the class entry, and `ModuleBuilder::class::<T>()` wires it to
`ClassMetadata<T>`. A class built by hand must park them:

```rust,ignore
// v0.15
.registration(|ce| MY_META.set_ce(ce))

// v0.16
.registration(|ce, arg_info| {
    MY_META.set_ce(ce);
    MY_META.set_arg_info(arg_info);
})
```

### `TryFrom<ModuleBuilder>`

Yields a third element, the allocations the `ModuleEntry` points into. The
`#[php_module]` macro stores it in the extension's `StaticModuleEntry`; only
code that calls `try_into()` by hand is affected.

```rust,ignore
// v0.15
let (entry, startup): (ModuleEntry, ModuleStartup) = builder.try_into()?;

// v0.16
let (entry, startup, owned): (ModuleEntry, ModuleStartup, ModuleAllocations) =
    builder.try_into()?;
```

### `IniEntryDef::register`

Takes a `&'static [IniEntryDef]` terminated by `IniEntryDef::end()` instead of a
`Vec`, because PHP 8.5 keeps the table as `zend_ini_entry.def` and the CLI SAPI
reads `def->value` at runtime. `IniEntryDef::new` is now a `const fn` taking
`&'static CStr`, so the table is a plain `static`.

#### Before (v0.15)

```rust,ignore
let entries = vec![IniEntryDef::new(
    "my_ext.enabled".to_owned(),
    "1".to_owned(),
    &IniEntryPermission::All,
)];
IniEntryDef::register(entries, mod_num);
```

#### After (v0.16)

```rust,ignore
static INI: IniEntryDefs<2> = IniEntryDefs::new([
    IniEntryDef::new(c"my_ext.enabled", c"1", IniEntryPermission::All),
    IniEntryDef::end(),
]);

IniEntryDef::register(INI.as_slice(), mod_num);
```

`IniEntryDefs<N>` exists because `IniEntryDef` holds raw pointers and an array of
them is not `Sync` on its own.
