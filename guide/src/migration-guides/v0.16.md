# Migrating to `v0.16`

## `Zval::set_resource` Requires an Unsafe Block

`Zval::set_resource` accepts a raw `zend_resource` pointer and transfers one
owned Zend reference into the zval, so callers must now uphold its safety
contract explicitly.

### Before (v0.15)

```rust,ignore
zval.set_resource(resource);
```

### After (v0.16)

```rust,ignore
// SAFETY: `resource` is a valid Zend-managed resource whose owned reference is
// transferred into `zval`.
unsafe { zval.set_resource(resource) };
```

The pointer must be non-null and valid until Zend releases the transferred
reference. `set_resource` does not increment the resource refcount, so the
caller must relinquish that reference after the call. Replacing a zval with the
same resource requires a separate incoming reference.

## SAPI Header Raw Constructors Removed

`SapiHeader::from_raw` and `SapiHeaders::from_raw` have been removed. These
constructors accepted unchecked Zend pointers through safe Rust.

ext-php-rs now copies the header data into owned snapshots before invoking the
`Sapi::send_header` and `Sapi::send_headers` callbacks.

### Before (v0.15)

```rust,ignore
let header = SapiHeader::from_raw(raw_header);
let headers = SapiHeaders::from_raw(raw_headers);
```

### After (v0.16)

Read header data from the snapshots supplied to your `Sapi` implementation:

```rust,ignore
fn send_header(_ctx: &mut MyContext, header: &SapiHeader) {
    if let Some((name, value)) = header.as_name_value() {
        // Send the header to the client.
    }
}

fn send_headers(
    _ctx: &mut MyContext,
    headers: &SapiHeaders,
) -> SendHeadersResult {
    let response_code = headers.http_response_code();
    SendHeadersResult::DoSend
}
```

Code that needs direct access to `sapi_header_struct` must use the raw FFI API
and uphold Zend's pointer validity and lifetime requirements itself.

## Void Return Type for Functions Without Explicit Return

Functions and methods without an explicit Rust return type now declare `void` as their PHP return type.

### Before (v0.15)

```rust,ignore
#[php_function]
pub fn do_something() {
    println!("Hello");
}
```

Generated PHP signature: `function do_something()` (implicit `mixed` return)

### After (v0.16)

The same Rust code now generates: `function do_something(): void`

### Migration

If your function actually returns a value but didn't declare it, you must now add the return type:

```rust,ignore
// Before: worked but was incorrect
#[php_function]
pub fn get_value() {
    42  // implicitly returned, but no declared type
}

// After: must declare return type
#[php_function]
pub fn get_value() -> i32 {
    42
}
```

### Exceptions

The magic methods `__destruct` and `__clone` are excluded from this change, as PHP forbids return type declarations on them.

## Mutable Accessors Require `&mut`

This closes [#461](https://github.com/extphprs/ext-php-rs/issues/461).

Several safe functions used to hand out a `&mut` derived from a shared `&`. That
let ordinary safe code hold two mutable references to the same zval at once,
which is undefined behaviour under Rust's aliasing rules. The signatures below
now require a mutable borrow so the compiler rejects that.

The affected functions are `ZendHashTable::get_mut`,
`ZendHashTable::get_index_mut`, `Zval::indirect_mut`,
`ExecutorGlobals::function_table_mut`, `Zval::traversable`, `Zval::iterable`,
`ClassEntry::get_iterator`, and `StreamWrapper::get` / `StreamWrapper::get_mut`.

### Mutable Hashtable Access

`get_mut` and `get_index_mut` take `&mut self`, so the binding must be mutable.

#### Before (v0.15)

```rust,ignore
fn bump(ht: &ZendHashTable) {
    if let Some(zv) = ht.get_mut("counter") {
        zv.set_long(1);
    }
}
```

#### After (v0.16)

```rust,ignore
fn bump(ht: &mut ZendHashTable) {
    if let Some(zv) = ht.get_mut("counter") {
        zv.set_long(1);
    }
}
```

The following no longer compiles, which is the point of the change:

```rust,ignore
let first = ht.get_mut("test").unwrap();
let second = ht.get_mut("test").unwrap();  // error[E0499]
first.set_long(2);
```

If you need to read two entries at once, take the second as a shared reference
with `get`, or finish with the first before requesting the second.

### Executor Globals

`function_table_mut` takes `&mut self`, so acquire the write guard rather than
the read guard.

#### Before (v0.15)

```rust,ignore
let table = ExecutorGlobals::get().function_table_mut();
```

#### After (v0.16)

```rust,ignore
let mut globals = ExecutorGlobals::get_mut();
let table = globals.function_table_mut();
```

`GlobalWriteGuard` already implements `DerefMut`, so no other change is needed.
Bind the guard to a variable, as the guard must outlive the borrow.

### Iterables and Traversables

`Zval::traversable` and `Zval::iterable` take `&mut self`, and `Iterable` is now
extracted through `FromZvalMut` instead of `FromZval`. Resolving the
`Traversable` variant invokes the Zend `get_iterator` handler, which mutates the
object, so a shared borrow was never sound.

Function signatures using `Iterable` as a parameter are **unchanged** and keep
working, because the macro already extracts arguments through `FromZvalMut`:

```rust,ignore
#[php_function]
pub fn count_items(mut iterable: Iterable) -> usize {
    iterable.iter().map_or(0, Iterator::count)
}
```

Only hand-written extraction needs updating.

#### Before (v0.15)

```rust,ignore
let iterable = Iterable::from_zval(zval);
let iterator = zval.traversable();
```

#### After (v0.16)

```rust,ignore
let iterable = Iterable::from_zval_mut(zval);
let iterator = zval.traversable();
```

where `zval` is now a `&mut Zval`. `ClassEntry::get_iterator` likewise takes
`&'a mut Zval` and ties the returned iterator's lifetime to it.

### Stream Wrappers

`StreamWrapper::get` and `StreamWrapper::get_mut` are now `unsafe`. They return a
reference into PHP's per-request stream wrapper table with a lifetime that is not
constrained by their arguments, and `get_mut` cannot verify that no other
reference to the same wrapper is live. This is the same class of change as
`Zval::set_resource` above.

#### Before (v0.15)

```rust,ignore
let wrapper = StreamWrapper::get_mut("http").unwrap();
```

#### After (v0.16)

```rust,ignore
// SAFETY: used within the current request, and no other reference to the
// `http` wrapper is live for the duration of this borrow.
let wrapper = unsafe { StreamWrapper::get_mut("http") }.unwrap();
```

Both functions also copy the name into a NUL-terminated C string before calling
into PHP. Previously they passed the bytes of a `&str` directly, and
`php_stream_locate_url_wrapper` scans the path until it reaches a character
outside `[A-Za-z0-9+-.]`, so it could read past the end of the string slice and
resolve the wrong wrapper.

### Threading `&mut` Through a Handler

The requirement can propagate up several frames. A realistic case: a function
that mutates entries of an array argument.

#### Before (v0.15)

```rust,ignore
#[php_function]
pub fn normalise(ht: &ZendHashTable) {
    rescale(ht);
}

fn rescale(ht: &ZendHashTable) {
    for key in ["width", "height"] {
        if let Some(zv) = ht.get_mut(key) {
            if let Some(value) = zv.long() {
                zv.set_long(value * 2);
            }
        }
    }
}
```

#### After (v0.16)

```rust,ignore
#[php_function]
pub fn normalise(ht: &mut ZendHashTable) {
    rescale(ht);
}

fn rescale(ht: &mut ZendHashTable) {
    for key in ["width", "height"] {
        if let Some(zv) = ht.get_mut(key) {
            if let Some(value) = zv.long() {
                zv.set_long(value * 2);
            }
        }
    }
}
```

`&mut ZendHashTable` is accepted as a `#[php_function]` parameter type, so the
PHP-facing signature does not change. If you cannot obtain a mutable borrow at
the outermost frame, the array is genuinely shared and mutating it was unsound
before this release.
